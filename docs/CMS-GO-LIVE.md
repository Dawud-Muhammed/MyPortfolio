# CMS go-live handbook

This describes the implementation in this repository. It does not mean the migration, environment configuration, or production deployment has already been performed. For migration and release details, also read [BACKEND.md](BACKEND.md), [RELEASE.md](RELEASE.md), and [RENDERING.md](RENDERING.md).

## The local preview is a snapshot, not your live CMS

`npm run dev:public` opens port **5175** in `public-preview` mode. Its Vite plugin reads the ignored `docs/live-public-snapshot.local.json`, substitutes a local Supabase endpoint, and serves captured public records. It rejects non-GET requests with HTTP 405. Login, editing, contact submission, and paid assistant answers are deliberately unavailable there. Saving something in the real CMS cannot update this snapshot automatically.

`npm run build` is the production build. The snapshot plugin is installed only for `command === 'serve' && mode === 'public-preview'`; it is not installed during a build. Production reads the configured Supabase project. Do not change production's build command to `dev:public`, commit the snapshot, or copy local preview URLs/placeholder keys into Vercel.

For local editing against an isolated configured database, use `.env.local` with placeholders replaced privately, run `npm run dev:api` and `npm run dev`, and use the ordinary development URL. `npm run preview` previews the built frontend; it does not by itself host the Vercel API functions.

## Prepare the deployment before pushing to the production branch

1. Back up the existing database and inspect its migration history. Apply `supabase/migrations/20261105090000_systems_studio.sql` to staging first, after the existing schema/migrations. Preserve real IDs, slugs, relationships, and media. **Do not import `supabase-export.sql` as Dawud content:** it includes unrelated template records. Do not replay historic seed operations onto production.
2. Provision the owner's real Supabase Auth UUID in `public.admin_users` using the SQL procedure in BACKEND.md. A normal authenticated account is intentionally insufficient. Verify owner access and non-owner denial in staging.
3. Configure the Vercel project's Preview environment using `.env.example`. Browser build-time values are `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`, and `VITE_SITE_URL`. The public URL/key must belong to the intended staging project. Server values include `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `SITE_URL`, and `ASSISTANT_SESSION_SECRET`. The HTML function uses `SUPABASE_ANON_KEY` if supplied, otherwise `VITE_SUPABASE_ANON_KEY`. Keep browser and server project URLs consistent.
4. Keep `ASSISTANT_ENABLED=false` initially. OpenAI credentials, reviewed pricing, model selection, and budget limits are server settings; never put them in `VITE_*`, CMS rows, or Git. Contact submissions also need the configured backend and session secret. The public Supabase anonymous key is intended for the browser; the service-role key is not.
5. Use Node **22.12 or newer**, `npm ci`, the checks listed in README, and `npm run build`. Keep the repository root as the Vercel project root, build command `npm run build`, and output directory `dist`. Deploy the repository with its `api/`, `server/`, and `vercel.json`; uploading only `dist` loses contact, assistant, and request-time HTML.
6. Review `git status --short` and `git diff`. Commit only reviewed source, migrations, documentation, and lockfile changes on a release branch such as `codex/studio-release`, then push that branch for review/preview. Do not commit `.env.local`, `.vercel`, credentials, or `.local.json` snapshots. A push to the configured production branch may trigger immediate deployment, so use the preview branch until the release is ready.
7. In the preview, test one isolated edit, publish, and unpublish; compare browser content and page-source HTML. Test real Auth/Storage permissions and contact validation against staging only. After production authorization, apply the reviewed migration to the backed-up production database, provision the production owner, set Production environment values, and release the reviewed commit through the existing Vercel workflow. Changing build-time `VITE_*` values requires a new build/deployment.

**Ordinary published CMS edits do not require a Git push or rebuild.** Code, dependency, migration, and environment changes do. Keep paid answers disabled until account/model access, pricing, and bounded staging evaluation are verified.

## What to edit in the CMS

Sign in at `/admin/login` on the configured staging or production site, not the read-only 5175 preview. Save the relevant section and check its publication switch.

- **Settings → Profile:** `profile.name` drives the large homepage name, About title, and copyright name. `title` is the professional focus; `profile_picture_url` is the real portrait; `bio` appears on About; `location` appears on Home/About/Contact; `timezone` appears beside the Contact location. `email`, `phone`, and `resume_url` drive direct contact and résumé links. Use `is_published=true` to make the record public. `assistant_eligible` separately approves profile/contact knowledge. `tagline` is available to the assistant and server fallback copy; it is not the main homepage statement.
- **Settings → Homepage composition:** edit `hero_content.kicker`, `headline`, `highlighted_word`, and `subheadline`. The highlighted phrase must occur exactly within the headline to be highlighted. `availability_label` contains the short truthful availability/proof text, and `availability_status` must be enabled to show it; this is separate from `profile.availability`. Publish the hero record.
- **Projects:** publish with `publication_status='published'`, enable `is_featured`, and set `order_index` ascending. Home selects the first **three** published featured projects; lower order values appear first. `status` (Live/In Progress/Archived) describes the product and does not publish it. Edit `title`, `excerpt`, description/case-study fields, images, evidence URLs, category, and verified technology relationships. Add technologies/categories in **Collections** and publish those records too. Preserve an existing `slug`; changing it changes its URL and does not automatically create a redirect.
- **Settings → Website/contact:** `site_name` and `logo_url` drive the navbar brand, and `footer_tagline` drives the optional footer line. Copyright is generated once from the current year and profile name. `whatsapp_enabled` and `whatsapp_number` control the Contact WhatsApp link; a nonempty `whatsapp_message` supplies its URL-encoded draft message. **Social Links** uses `platform`, `url`, `is_visible`, `is_published`, and ascending `order_index`. The footer shows up to three visible HTTPS social links.
- **Navigation:** edit `label`, `target`, `location='navbar'`, `order_index`, `is_visible`, and `is_published`. Supported header targets are `/`, `/about`, `/projects`, `/services`, `/blog`, `/gallery`, `/contact`. Use order 0–6 for that intended sequence. With no eligible header rows, the standard navigation is restored; a partially populated collection shows only the matching rows. Footer-location navigation rows are not currently consumed by the footer.
- **Settings → SEO:** publish `site_title_template` (use `%s` for the page title), `meta_description`, `og_image_url`, `twitter_handle`, and `gsc_verification` (the verification value, not a pasted HTML tag). Home uses the default description; inner pages supply their own descriptions or record-specific `seo_title`/`seo_description`. Canonical origin comes from `SITE_URL`/`VITE_SITE_URL`, not CMS. Check both initial HTML and client navigation after edits.
- **Blog:** use exact `status='Published'`. Apply the follow-up migration `20261105110000_restore_undated_published_articles.sql` after the base Systems Studio migration: it restores explicitly published legacy articles with unknown dates. They display “Publication date not recorded.” Drafts and future-dated articles remain private. New publication through the CMS still requires a date. Do not invent dates or auto-fill today's date for old articles. Reading time is computed from content. Gallery requires a descriptive `caption` and `alt_text`; `related_url` is optional. Services can reference published project IDs through `evidence_project_ids`.
- **AI Guide:** edit `assistant_settings.greeting`, `suggested_questions`, optional real `portrait_url` override, `greeting_audio_url`, and `audio_is_synthetic`. Empty portrait uses the public profile portrait. Clear the audio URL to disable speech; the bundled default is `/audio/introduction.wav`. Keep the text greeting and spoken recording identical. The CMS `enabled` switch and server `ASSISTANT_ENABLED` must both allow paid requests, and all server safeguards must be ready. The kill switch does not require an OpenAI request.
- **Approved knowledge:** only published, `assistant_eligible=true` records from profile, projects, services, experience, and FAQs are retrieved. Merely publishing a record does not approve it for the assistant. Contact submissions and comments are excluded. Review usage in AI Guide; budget/model changes remain in server configuration.

### Media

The CMS uploader accepts JPEG/PNG/WebP/AVIF images up to 5 MB into `portfolio-images`; résumé PDFs up to 10 MB into the existing case-sensitive `Portfolio-documents` bucket; and MP3/WAV/OGG/M4A audio up to 10 MB into `portfolio-audio`. Save the owning CMS record after upload. Clearing the field removes the reference, not the stored object. Public asset URLs stay public even if their content row is unpublished; do not upload private draft assets to a public bucket. Project videos currently use an existing URL field rather than a dedicated video uploader.

## When an edit becomes visible

- Successful CMS writes invalidate this browser's public cache and notify other same-origin tabs through local storage. Visible public pages fetch again every 30 seconds and on focus/visibility restoration. Browser timers can be delayed in background tabs; a failed refresh clears the affected collection rather than retaining potentially unpublished content.
- Vercel `api/page.js` fetches published content anonymously for each HTML request and sends `no-store` headers. There is no content rebuild webhook to run. Public sitemap and detail pages use the same publication boundaries.
- The assistant retrieves eligible knowledge for each paid question and checks `content_revision` before and after generation. An open panel polls configuration/revision every 30 seconds and clears older conversation display when it observes a changed revision. It cannot erase information already copied by a visitor.
- GitHub contributions are separate public API data. `GITHUB_USERNAME` is currently the code constant `Dawud-Muhammed` in `src/lib/github-contributions.ts`; changing a CMS social link does not change the graph account. Browser data is cached for 15 minutes and the upstream source may cache up to an hour. Counts are not CMS fields or real-time guarantees.

## Current limitations and useful edge-case checks

- **Multiple singleton records:** Settings selects the newest row by `created_at DESC, id DESC`; public singleton reads select the newest **published** row using that order. If the newest record is a draft, the public site can still show an older published record. Keep one authoritative published profile/hero/website/SEO record; inspect duplicates in staging while preserving IDs/references. No automated deletion occurs. A missing singleton cannot currently be created through Settings and needs controlled database setup.
- **Availability:** disable `hero_content.availability_status` to hide its line in both browser and initial HTML. `profile.availability` does not control that homepage line.
- **Blog knowledge eligibility:** the Blog `assistant_eligible` switch does not add articles to the current retrieval allowlist. That requires a deliberate backend change, not more CMS saves.
- **Fixed interface copy:** “Hey, I’m”, “SYSTEMS STUDIO”, section headings, form labels, primary actions (“View Selected Work” and “Contact Me”), assistant launcher name (“Dawud's AI Assistant”), and GitHub panel captions are code-owned. Missing public hero/profile fields also reveal intentional fallback copy. The CMS is not a general editor for every visible word.
- **Wrong content or seemingly unchanged edits:** confirm the deployed commit and domain; compare the browser and server Supabase project IDs; ensure Preview and Production environments are not mixed; confirm you are not on port 5175; verify the row's publication flag and save result; then refocus or reload. If the network reports unknown columns/RPCs, the new migration has not reached that database—do not solve this by removing publication filters or weakening RLS.
- **Missing work/media:** check featured flag, publication, ordering and the three-project limit; publish related technology/category records; confirm actual public storage URLs and bucket permissions; supply missing image/caption fields. Empty/draft records should not be replaced with invented work or template seed data.
- **Authentication and API errors:** signed-in does not mean administrator; check `admin_users` membership and migration before changing access controls. An empty FAQ/disabled guide can mean the server is unconfigured or no knowledge was approved. Contact success means saved to the private portfolio inbox; there is no promised email forwarding integration. A contact timeout is delivery-unconfirmed, so check the inbox before resending.

Run all edit/publish/unpublish, role, upload, and message tests against isolated staging records. Keep production verification read-only until the actual release is authorized.

The local release-readiness check passes application/node type checks, lint, build, 57 automated checks and all 18 browser scenarios. Tests use isolated or synthetic data; they do not certify the unconfigured hosted production environment. No production migration, push, deployment, message delivery or paid model call was made.
